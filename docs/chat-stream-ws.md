# Спека: WebSocket-ручка живой ленты чата

Назначение — отдавать командному сайту новые сообщения чата в реальном времени,
чтобы страница, один раз загрузив историю по REST, дальше показывала новые
сообщения сразу, без поллинга.

Ручка — продолжение уже существующего REST истории чата
(`GET /api/v1/chats/...`). Формат сообщения в кадре **байт-в-байт совпадает** с
элементом ответа `GET /api/v1/chats/{chat_id}/messages` (схема `MessageOut`,
см. OpenAPI `/api/v1/docs`).

## Эндпоинт

```
WSS /api/v1/chats/{chat_id}/ws
```

- `chat_id` — telegram id чата (целое, может быть отрицательным для групп), тот же,
  что в REST.
- Транспорт — WebSocket (текстовые кадры, JSON в UTF-8). Снаружи проксируется
  через nginx под префиксом `/api/v1/` — нужен апгрейд соединения (см. ниже).

## Авторизация

Тот же сервисный Bearer-токен, что и у REST. Поддерживаются два способа (нужен
любой один):

- **Query-параметр** `token=<токен>` — для браузера: нативный `WebSocket` не умеет
  ставить заголовки.
- **Заголовок** `Authorization: Bearer <токен>` — для серверного прокси.

При отсутствующем/недействительном/отозванном токене сервер принимает соединение
и сразу закрывает его с кодом **4401** (трактовать как «не авторизован»).

## Параметры запроса (query)

| Параметр   | Тип  | Обяз. | Описание |
|------------|------|-------|----------|
| `token`    | str  | усл.  | Сервисный токен (если не передан в заголовке `Authorization`). |
| `after_id` | int  | нет   | Наибольший `tg_message_id`, который клиент уже отрисовал из REST-истории. Сервер при подключении дошлёт все сообщения с `tg_message_id > after_id`, затем перейдёт на живой поток. Закрывает «дыру» между загрузкой истории и открытием сокета. |

## Кадры сервер → клиент

Каждый кадр — JSON-объект с полем `type`:

```jsonc
// новое сообщение (входящее от участника или исходящее от Гоги)
{ "type": "message.new",    "message": { /* MessageOut */ } }

// изменение ранее доставленного сообщения: правка текста ИЛИ догрузка медиа
// (у медиа появился url). Тот же tg_message_id, что был раньше.
{ "type": "message.edited", "message": { /* MessageOut */ } }

// heartbeat (~раз в 25 c), чтобы прокси не рвал простаивающее соединение.
// Можно игнорировать, отвечать не нужно.
{ "type": "ping" }
```

`message` — объект `MessageOut`. Ключевые поля (полный перечень — в OpenAPI):

| Поле | Тип | Описание |
|------|-----|----------|
| `chat_id` | int | id чата |
| `tg_message_id` | int | telegram message_id — **ключ дедупликации и сортировки** |
| `direction` | `"incoming"` \| `"outgoing"` | от участника / от Гоги |
| `date` | str (ISO-8601) | момент отправки |
| `edit_date` | str \| null | момент правки |
| `sender_user_id` | int \| null | id отправителя |
| `sender_username` | str \| null | username отправителя (снимок) |
| `sender_name` | str \| null | отображаемое имя (снимок) |
| `text` | str \| null | текст или подпись к медиа |
| `entities` | array \| null | форматирование (telegram entities) |
| `reply_to_tg_message_id` | int \| null | на какое сообщение ответ |
| `forward_origin` | object \| null | источник пересланного |
| `forward_sender_name` | str \| null | имя источника пересылки |
| `media_group_id` | str \| null | id альбома |
| `content_type` | str | тип содержимого (значение aiogram ContentType) |
| `media` | object \| null | медиавложение (см. ниже) |

`media` (когда есть вложение):

| Поле | Тип | Описание |
|------|-----|----------|
| `media_type` | str | `photo` / `video` / `animation` / `document` / `audio` / `voice` / `video_note` / `sticker` |
| `file_unique_id` | str | стабильный id файла |
| `url` | str \| null | путь для скачивания байтов, **относительный** (`/api/v1/chats/{chat_id}/media/{file_unique_id}`); `null`, пока не скачано |
| `mime_type`, `file_name`, `file_size`, `width`, `height`, `duration` | — | метаданные (могут быть null) |
| `downloaded` | bool | скачаны ли байты |

### Пример

```json
{
  "type": "message.new",
  "message": {
    "chat_id": -1002985203390,
    "tg_message_id": 12345,
    "direction": "incoming",
    "date": "2026-06-04T09:15:30+00:00",
    "edit_date": null,
    "sender_user_id": 161423914,
    "sender_username": "Kademn",
    "sender_name": "Денис К.",
    "text": "Гога, смени ведущего",
    "entities": null,
    "reply_to_tg_message_id": null,
    "forward_origin": null,
    "forward_sender_name": null,
    "media_group_id": null,
    "content_type": "text",
    "media": null
  }
}
```

## Кадры клиент → сервер

Не требуются. Сервер игнорирует входящие прикладные кадры (пинговать его не
нужно). Браузер сам отвечает на protocol-ping pong'ом.

## Гарантии доставки

- **At-least-once.** Одно сообщение может прийти дважды (например, перекрытие
  добора по `after_id` и живого потока). Клиент **обязан** делать upsert по
  `tg_message_id`; `message.new` и `message.edited` обрабатываются одинаково —
  «вставить-или-заменить и перерисовать».
- **Порядок** обычно по возрастанию `tg_message_id`, но строго не гарантируется —
  вставляйте по `tg_message_id`, чтобы держать порядок.
- **Медиа.** Сообщение с вложением может сперва прийти с `media.url = null`
  (байты ещё качаются) — показывайте плейсхолдер. Когда скачивание завершится,
  по тому же `tg_message_id` придёт `message.edited` с заполненным `media.url`.
  Часть медиа не скачивается никогда (больше 20 МБ или ошибка) — тогда
  `downloaded` остаётся `false`, `url` — `null`.
- **Возможна потеря при медленном клиенте.** Если клиент не успевает читать,
  сервер дропает кадры (не копит бесконечно). Это безопасно: при реконнекте с
  `after_id` пропуск добирается.

## Рекомендуемый сценарий клиента

1. `GET /api/v1/chats/{chat_id}/messages?limit=50` → отрисовать; запомнить
   `newest_id` из ответа.
2. Открыть `WSS /api/v1/chats/{chat_id}/ws?token=…&after_id=<newest_id>`.
3. На каждый кадр: `ping` — игнорировать; иначе upsert сообщения по
   `tg_message_id` и перерисовать.
4. При `close`/`error` — реконнект с backoff, передавая `after_id` = максимальный
   увиденный `tg_message_id` (добор пропуска за время простоя).
5. Прокрутка вверх (старая история) — по-прежнему через REST
   `?before_id=` / `has_more`. WebSocket — только «живой хвост», старую историю
   по нему не отдаём.

## Коды закрытия

- `4401` — не авторизован (нет/неверный/отозванный токен).
- `1000` / `1001` / `1006` и прочие — обычное закрытие/обрыв → реконнект по п.4.

## Требование к nginx (серверная сторона)

Ручка под уже проксируемым префиксом `/api/v1/`, но для апгрейда соединения в
`location`, который ведёт на API, нужны:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 3600s;   # дольше интервала heartbeat
```

## Вне объёма (сознательно не делаем)

- Событий «сообщение удалено» нет (Telegram не уведомляет об удалении надёжно;
  в истории удалённые сообщения остаются).
- Нет typing/печатает, read-receipts, presence.
- Нет фильтрации, кроме как по `chat_id`.
- Полная история по WebSocket не проигрывается — она в REST.
